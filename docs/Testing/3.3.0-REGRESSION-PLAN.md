|---|---|

Every module in the app was touched. This is not a point release with a few fixes, and it
should not be regression-tested like one.

### The four whole-app changes

These carry more risk than any individual feature, because their failure mode is a crash, a
hang, or a silently wrong persisted value rather than a wrong screen — so no feature row
catches them. They are matrix rows **PR1–PR4**:

1. **Swift 6 language-mode flip** (31 `fix(swift6)` commits + `SWIFT_VERSION` 5.0 → 6.0).
   Strict concurrency converts previously-silent main-actor violations into hard traps. The
   regression signal is a *new crash class*, not a changed screen.
2. **Readium 3.9.0 → 3.11.0** (PP-4848). A reader-engine swap can change locator encoding
   without changing a single Palace source line — invisible to a diff-scoped review and to
   every unit test that round-trips through our own types.
3. **iOS 17 deployment floor** (16.0 → 17.0, both targets + 7 SPM packages). Newer-OS-only
   API adopted since must degrade rather than crash on the floor.
4. **Package extraction, decomp Waves 1–3** (`PalacePreferences`, `PalaceFeatureFlags`,
   `PalaceBookModel`, `PalaceBookRegistry`, Accounts/Downloads seams). Each wave claimed to
   be behavior-preserving and each was gated on a green suite — but moving a singleton read
   behind a protocol changes *when* state resolves, which a suite can miss. Credential
   isolation (**A6**) is the highest-consequence cell.

## 3. Coverage audit — what was missing, and what was done about it

The audit asked one question per surface: does a patron-reachable change since 3.2.0 have a
matrix row, a journey, and a unit test?

**The unit layer kept pace.** 712 test files changed in the same window; every feature probed
(rating, sideload, skip interval, sleep timer, skeletons, mini-player, rotor a11y, footnotes,
keychain corruption, catalog branding, offline catalog state, feature-flag gates) resolved to
real test files. The one surface with no direct unit coverage is the `HelpButton` entry point.

**The release-regression layer did not.** The matrix was last re-derived on 2026-07-08 and had
zero rows for surfaces a patron can now reach. Two concrete defects were found and fixed:

### Finding 1 — 26 patron-reachable surfaces had no matrix row

Added (matrix went 66 → 92 rows): `PR1–PR4`, `E9`/`E10`,
`E3-Skip/Sleep/Speed/Mini/Icons/Stream`, `C5–C7`, a new **Support & Feedback** section
(`S1–S4`, `R1–R2`), `U3-Footnote/PrintPage/WhereAmI/BlockNav/SearchFocus`, `U5`/`U6`, and
`X7–X9`. See the matrix change log for the full derivation.

### Finding 2 — 8 of 33 recorded journeys never ran

`~/harness/palace-qa/.simdrive/regression-areas.json` is the shard key: a campaign worker is one
`(area-group × device-cell)`, and a journey no area group claims is never fanned to any cell.
Eight journeys existed on disk, passed their own lint, and **were executed by nothing**:

```
PP-4529-print-page-navigation-voiceover   app-rating-sentiment-gate
audiobook-sleep-timer-45                  holds-reservations-empty
reader3-pdf-open-and-page                 triage-bot-category-chip-rapid-tap
triage-bot-redaction-adversarial-input    ws4-ipad-on-mac-exit-adobe-drm
```

That list includes **`triage-bot-redaction-adversarial-input`** — the guard against sending a
patron's typed password or card number to a support queue. It was recorded, committed, and
dormant.

A journey no cell claims is indistinguishable from a journey that passes. Fixed by adding a
`support` area group and adopting the orphans into the groups that own their matrix rows.
`ws4-ipad-on-mac-exit-adobe-drm` is the one legitimate exception — it is an interactive
protocol driven by `~/harness/palace-qa/scripts/regression-ipad-on-mac.sh`, not a replayable recording — and the
manifest now records *why* it is unassigned so the next audit does not "fix" it.

### Finding 3 — a stale device-cell label

`C-ios18` was documented as the "back-compat floor (iOS-16 substitute)". The floor is now
iOS 17.0. The cell sits one minor version *above* the floor rather than substituting for it.
Corrected in the manifest; matrix row **PR3** owns the true-floor check.

## 5. Execution plan

Five legs. Legs A and B are done; the rest need a driven device or simulator.

| Leg | Scope | Tool | State |
|---|---|---|---|
| **A — Unit + integration** | Full `Palace` scheme, both test targets, CI parity (`-test-iterations 3 -retry-tests-on-failure`) | `scripts/xcode-test-optimized.sh` | ✅ **Passed** — see §6 |
| **B — Tooling gates** | Manifest integrity, detector pytests, hook wiring | `pytest scripts/tests/` | ✅ 52 passed |
| **C — Journey replay** | Every journey in every area group, per device cell | `~/harness/palace-qa/scripts/simdrive-regress.sh`, `~/harness/palace-qa/scripts/regression-area-worker.sh` | ⛔ **Blocked** — see §8 |
| **D — Chaos (PRIMARY)** | Adversarial exploration, all 7 area groups × 3 cells | `~/harness/palace-qa/scripts/regression-chaos-fan.sh` | Running — see §9 |
| **E — Manual matrix** | P0 → P1 → P2 side by side against 3.2.0; everything marked Manual, especially `UP1` (in-place upgrade) and the VoiceOver rows | Human + `simdrive` | Pending |

**Leg E is not optional and not substitutable.** The rows that carry the most consequence —
in-place upgrade over real 3.2.0 state, VoiceOver rotor navigation, Adobe/LCP fulfillment on a
real device, CarPlay — are the ones no automation reaches. Readium renders into a WKWebView
that XCTest cannot see; rotor items do not appear in screenshots; and `UP1` requires prior-version
state that a clean install cannot manufacture.

## 8. Leg C is blocked: the replayable corpus is gone (F-INFRA-001)

The fleet campaign was fanned for real: 7 area groups × 3 simulator cells = 21 shards, against
freshly provisioned, ad-hoc-signed candidate installs on iPhone 16 Pro / iOS 26.0, iPad Pro 11″
/ iPadOS 26.1, and a purpose-created iPhone 16 Pro / iOS 18.0.

Every shard finished in under thirty seconds and reported **0 findings**. That is not a pass.

```
96  [SKIP] lines across 21 shards
 0  journeys executed
 0  evidence logs written
 0  findings
```

Two skip reasons, one of which is structural:

- `no recording at ~/.simdrive/recordings/<id>/recording.yaml` — the majority.
- `not stageable (staging_status=blocked: phase2 borrow-gated)` — journeys needing a borrowed
  book on a signed-in library.

**The two artifacts are not the same thing.** `~/harness/palace-qa/.simdrive/journeys/<id>.yaml` is a *scenario
definition* — declarative, committed, 33 of them. `~/.simdrive/recordings/<id>/recording.yaml`
is a *replayable recording* — device, OS version, app version, concrete steps, SSIM masks — and
it lives in a machine-local directory that is not in the repo. The area-worker replays the
second. Of the 32 journeys the manifest now references, **1 has a recording on this machine.**

`RECORDING_COVERAGE_GAP.md`, stamped 2026-07-08, reports 22 of 25 recorded and calls the corpus
"near-complete". The store today holds eight entries, seven of them chaos recordings, and one
manifest journey. No backup exists anywhere under `$HOME`.

So the executable regression corpus is not reproducible from a clean checkout. It exists only
where somebody happened to record it, it was lost without anything failing, and the harness's
response to its own absence is a silent skip followed by a green summary. That last part is the
part worth fixing regardless of the recordings: **a campaign that skips 96 of 96 journeys must
not be able to emit "0 findings"** — the merged `findings.csv` and `report.html` from this run
would read as a clean regression pass.

Recorded as **F-INFRA-001** (blocker) in `.regression-runs/rc-3.3.0-20260820/findings.csv`,
with the skip log, the present-recordings listing, and the computed missing list as evidence.

### What was established instead, by driving the candidate live

Live `simdrive` on the C-iphone-26 cell against `ff3b1227c`, with no crash reports generated
during the session:

- App cold-launches and the catalog loads real content over the network.
- Installs and launches cleanly on all three cells — including iOS 18.0, which is the nearest
  available proxy for the raised iOS 17 floor (**PR3** partial evidence; no iOS 17 runtime is
  installed on this machine).
- **E3-Skip** — Settings → Playback exposes Skip Forward and Skip Back as independent controls,
  both at 30 seconds, with copy confirming they apply to all audiobooks.
- **S4 / X7** — Settings → Support exposes "Get Help" and the "Include diagnostics" toggle with
  its explanatory copy; "Advanced" is present and always visible.
- Settings → Advanced shows Developer Tools and Data & Reset, but **no "Testing" row**, so the
  Hidden Libraries toggle behind **X8** was not reachable this way even with
  `showDeveloperSettings` seeded. X8 remains unconfirmed on the candidate.

## 9. Strategy: chaos and live driving replace the QA pass; replay is not rebuilt

Owner decision, taken after §8: **do not rebuild the recorded corpus for this release.**
Chaos is the more effective discovery layer, and the record backs that rather than just the
intuition:

- The prose-stated-password leak in the support chat was found by a chaos agent **after** the
  unit tests for redaction passed. That is the single highest-severity defect the triage-bot
  work produced, and deterministic tests did not see it.
- Both independent reproductions of the Hidden Libraries deadlock (**X8**) came from chaos
  agents, from different directions on different simulators.
- A replay asserts that a known path still looks the way it looked. It cannot find a defect
  nobody has already walked into. For a release that changed 584 production files across all
  29 modules, the unknown-unknowns dominate.

Chaos also sidesteps the §8 blocker by construction: `chaos_seeds` are `<flow>/<step>`
*navigation hints* that the agent steers toward live, not recordings it replays. A missing or
`PENDING_CAPTURE` fixture is still a valid seed. Nothing in the chaos path reads
`~/.simdrive/recordings/`.

**This run therefore replaces the human QA regression pass**, and is scoped to match one:
7 area groups × 3 device cells, budget 20 paths / 12 minutes per area, on freshly provisioned
ad-hoc-signed candidate installs. Hard rules carried through from the chaos contract: Palace
Bookshelf is the only borrow library, no `simctl erase`, no credential lockout, and **every
finding requires log evidence** — no evidence, no finding.

### What chaos structurally cannot reach

Stated plainly, because a chaos pass reporting "no findings" in these areas would mean it never
went there — the same vacuous-green shape as §8:

| Row | Why chaos cannot cover it |
|---|---|
| **UP1 / UP1-Result** | Needs real 3.2.0-written state on disk, then an in-place upgrade. A chaos agent starts from the candidate; it cannot manufacture prior-version state. |
| **U3-Footnote / WhereAmI / BlockNav / SearchFocus** | VoiceOver rotor items are not in the accessibility tree the driver observes and do not appear in screenshots. |
| **X2 CarPlay** | Separate headless XCTest cell, not a driven UI. |
| **N1–N4 push** | Needs a Firebase service account and a real APNs round trip. |
| **PR2 locator round-trip across versions** | Same prior-version-state problem as UP1. |
| **E10 position cadence** | Requires ≥45 minutes of untouched locked playback; exceeds any chaos budget. |
| **Real-device DRM** | Adobe RMSDK / LCP behave differently on device than on simulator. |

These are driven manually after the chaos fan completes, or explicitly deferred. They are not
covered by silence.

## 7. What this plan does not cover

Stated so the gaps are chosen rather than discovered:

- **Real-device DRM.** Adobe RMSDK and LCP fulfillment behave differently on device than on
  simulator. Leg C/D evidence is simulator evidence.
- **LCP audiobook streaming** (PP-4957) ships with its flag **false**. Row `E3-Stream` verifies
  the flag-off path. The streaming path was accepted on simulator evidence and still owes a
  device pass before it is ever enabled.
- **CarPlay** (`X2`) runs as a headless XCTest cell, not a driven UI.
- **Push notifications** (`N1`–`N4`) need a Firebase service account and a real APNs round trip.
- **Mutation testing** is not run per-PR in CI; the release regression is the only place a
  mutation signal is produced for the candidate. It is not yet run here.
