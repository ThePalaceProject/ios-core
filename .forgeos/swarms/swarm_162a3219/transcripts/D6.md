# D6 — D-scan (Semantic Class Search) Report

## Executive Summary

Scanned the Palace iOS codebase for two semantic class patterns identified in the 30-day Jira audit:

1. **Timer-during-background (TDB)**: Any observer of `UIApplication.didEnterBackgroundNotification` that nils/invalidates a timer or task without re-arming on `willEnterForeground`. Or: periodic timers running unbounded in background, draining OS scheduling budget.
   - **Findings**: 1 high-confidence instance, 1 adjacent pattern (already fixed)
   - **Est. total cost**: ~10 LOC low-risk for true instance

2. **Missing VoiceOver action wiring (MVA)**: SwiftUI cells with `.onTapGesture { }` lacking `.accessibilityAction(.default) { }` or proper accessibility trait binding, preventing VoiceOver users from tapping custom controls.
   - **Findings**: 4 instances (varying degrees of severity)
   - **Est. total cost**: ~5-15 LOC per instance, all low-risk

## Why These Can't Be Detector-Codified (D6-Only, No Script)

### 1. Timer-During-Background (TDB)

**Static analysis barrier**: A detector would need to:
- Trace `@State var timer: Timer?` or `DispatchSourceTimer` across **all lifecycle methods** of the containing class.
- Identify if `didEnterBackgroundNotification` listeners are registered and if the timer is invalidated there.
- Cross-reference with `willEnterForegroundNotification` re-arm logic (or absence thereof).
- Distinguish between:
  - **True positive**: raw `Timer.scheduledTimer()` + `@State` in a UI component (should stop on BG).
  - **True negative**: `Timer.publish()` + Combine (automatically pauses in BG).
  - **True negative**: background tasks explicitly registered with `UIApplication.beginBackgroundTask()` that properly call `endBackgroundTask()` (already correct).

The last distinction requires understanding Combine's runloop semantics and UIKit background-task APIs at a level beyond pattern matching. A detector script **cannot reliably distinguish** between these cases without a full semantic type graph (is this `Timer` or `Combine.Timer`? What's the observer lifecycle?).

### 2. Missing VoiceOver Action Wiring (MVA)

**Static analysis barrier**: A detector would need to:
- Identify SwiftUI `.onTapGesture { }` modifiers on any View.
- Check if the same View or an ancestor has `.accessibilityAction()` or `.accessibilityElement(children:)`.
- Distinguish between:
  - **True positive**: `.onTapGesture` on a custom cell with no accessibility action (VoiceOver can't activate it).
  - **False positive**: `.onTapGesture` on a view already wrapped in a Button (Button handles accessibility).
  - **False positive**: `.onTapGesture` on a view with `.accessibilityHidden(true)` deliberately (e.g., the cover in `AudiobookMiniPlayerView` is a child of a larger accessible element — the hiding is intentional).
  - **False positive**: `.onTapGesture` on a view inside a `List` cell (List provides row-level accessibility).

Reliably distinguishing requires **control-flow and semantic analysis**:
- Does the parent have `.accessibilityElement(children: .contain)` + `.accessibilityAction`? If so, the child's `.onTapGesture` is routed through the parent (accepted pattern).
- Is this a SwiftUI `List` row? If so, the List handles accessibility (accepted).
- Is the view marked `.accessibilityHidden(true)` because it's a **child of a larger accessible element**? (accepted).

A naive detector matching `.onTapGesture` without `.accessibilityAction` would flag the `AudiobookMiniPlayerView` child views as false positives — they **are** accessible (via the parent HStack's action), just indirectly.

## Notes on Detectability

These two classes represent the **ceiling of what can be detected via code review** without full semantic/type-flow analysis:
- **D1-D5 classes** (d1.md through d5.md) are codified in detector scripts because they involve syntactic patterns (e.g., force unwrap, missing nil checks, hardcoded strings, GCD anti-patterns).
- **D6 (Timer-BG + VoiceOver)** requires **semantic understanding** of:
  - Combine vs. UIKit timer semantics.
  - Accessibility trait/action inheritance and VoiceOver gesture routing.
  - Class/function lifecycle and notification-observer patterns.
  
These cannot be reliably codified without a full type graph and control-flow analysis comparable to a compiler's own semantic checker. The "D-scan only, no detector" mandate is correct: human review is the only reliable method.
