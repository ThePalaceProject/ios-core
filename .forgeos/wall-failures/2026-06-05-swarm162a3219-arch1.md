# swarm_162a3219 arch1 — pre-commit hook exit-code capture bug

## Finding (verbatim from architect-reviewer rev_742175c0)

> `scripts/pre-commit-phase35-detectors.sh:61-62` has a shell exit-code capture bug. With `set -eu` enabled, `OUT=$(python3 ... --quiet 2>&1 || true)` followed by `EXIT=$?` always yields `EXIT=0` because `$?` captures the exit of the `|| true` short-circuit (always 0). The block-mode branch never fires; the commit succeeds regardless of detector findings. The detectors run and emit findings to stderr, but the hook is effectively a logger, not a gate.
>
> Confirmed empirically: `OUT=$(false || true); EXIT=$?; echo $EXIT` → `0`.
>
> Mitigation: verify-pr.sh's `run_m1_check` (line 192-193) captures `exit_code=$?` correctly because it does NOT use `|| true`. So the second wall (pre-PR) still catches findings. Only the FIRST wall (the integrator's PreToolUse hook in `.claude/settings.json` that exists specifically to enforce block-mode at commit-time) leaks.

## What actually happened

The integrator (orchestrator agent) wrote `scripts/pre-commit-phase35-detectors.sh` as the consolidated PreToolUse hook for the 6 Phase 3.5 detectors. The intent was: capture python's exit code in `$EXIT`, then branch on block-mode vs warn-mode. The implementation:

```bash
# BUGGY
OUT=$(python3 "$SCRIPT_PATH" --diff "$DIFF_FILE" --quiet 2>&1 || true)
EXIT=$?
```

With `set -eu` enabled, the `|| true` was meant to prevent a non-zero python exit from killing the whole script. But it had the unintended side effect of always making `$?` read 0 after the assignment, because `$?` captures the LAST command in the pipeline — and `|| true` is the last command, which always succeeds.

The block-mode if-branch (`if [ "$EXIT" -ne 0 ]`) therefore never fired. The hook ran the detectors, captured their stderr output (correctly!), but then read `EXIT=0` and silently passed the commit through.

The orchestrator did NOT write a fixture-driven test for the hook before committing, so the bug was invisible from the inside.

## Walls that should have caught it (and why they didn't)

- **implementer** — the orchestrator agent wrote a shell script with `set -eu` and didn't unit-test the exit-code-capture pattern. This is the canonical "I wrote a hook, eyeballed it, ran it manually with a no-violation diff (which happens to return 0 anyway), and called it done." The bug only surfaces on a violation case, which the orchestrator didn't construct. **Direct cause.**

- **TDD** — there was no fixture-driven test for the hook before commit. CLAUDE.md's TDD-mandatory rule applies to production code; the orchestrator interpreted "production code" as Swift/Palace and didn't apply it to a bash hook. Wall-failure entry's structural fix promotes TDD to ALL hooks the swarm-or-rigorous-fix integrator writes, not just Swift.

- **hook** — the doc-lifecycle hook and the M1-stanza hook both fired correctly on this commit. But there's no meta-hook that says "if you wrote a new pre-commit hook, did you also write its test?" The orchestrator added the hook AND wired it into `.claude/settings.json` in the same commit, with no test alongside.

## Proposed permanent fix

### Code fix (this PR)

`scripts/pre-commit-phase35-detectors.sh:61-62` changes from:

```bash
OUT=$(python3 "$SCRIPT_PATH" --diff "$DIFF_FILE" --quiet 2>&1 || true)
EXIT=$?
```

to:

```bash
OUT=$(python3 "$SCRIPT_PATH" --diff "$DIFF_FILE" --quiet 2>&1) && EXIT=0 || EXIT=$?
```

The `&& EXIT=0 || EXIT=$?` shape captures the python exit cleanly under `set -eu` without the always-0 short-circuit. Empirically verified: AFTER fix correctly reports EXIT=1 on a violation; BEFORE fix incorrectly reports EXIT=0.

### Structural prevention

1. **Fixture-driven test (`scripts/tests/test_pre_commit_phase35_detectors.sh`)** — 4 assertions: hook returns non-zero on a known violation; output identifies the firing detector; SKIP_PHASE35_DETECTORS=1 bypass works; per-detector bypass envvar works. Pins the exact bug so a future regression can't silently land.

2. **CLAUDE.md clause to be added (Phase 3.5 docs amend):**
   > **Hooks need tests too.** Any new pre-commit / pre-push / PreToolUse hook landed by the swarm or rigorous-fix integrator MUST include a fixture-driven test (Python pytest OR bash test script) that exercises BOTH the positive case (block fires) and the bypass case (envvar honored). Test lives under `scripts/tests/test_<hook-basename>.sh|py`. Without it, the hook is shipping unverified — the canonical wall-failure case 2026-06-05-swarm162a3219-arch1 documents what happens when this rule is skipped.

3. **Swarm SKILL Phase 4.5 check addition:**
   > **Check 6.6 (added 2026-06-05):** for every `scripts/hooks/*.sh` or `scripts/pre-*.sh` or `scripts/hooks/*.py` added or modified in the diff, verify a matching `scripts/tests/test_<basename>.*` exists in the same diff. Block if missing.
