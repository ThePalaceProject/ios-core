# Wave 3 Module A test name claims production-seam wiring but body bypasses production driver — same arch1 shape as cs_847892e8

## Finding (verbatim from architect rev_bc20951b)

> testPresenter_TPPReauthenticatorPath_invokesPresentationViaSafelyPresent at PalaceTests/SignInLogic/SignInModalLifecycleTests.swift:225 is a fake-wiring test — exactly the failure mode CLAUDE.md DoD check #7 was added to prevent. The name claims TPPReauthenticatorPath but TPPReauthenticator is never instantiated. The name claims invokesPresentationViaSafelyPresent but the fake driver short-circuits BEFORE the production driver chain reaches TPPPresentationUtils.safelyPresent at SignInModalView.swift:171. Test docstring even admits: "We bypass the real static API by injecting a fake driver".

## What actually happened

CLAUDE.md DoD check #7 landed in PR #1022 (wave 2). It says: "for every test name claiming to exercise a multi-step path through production code, line-coverage report must show non-zero hits on the cited lines from that test."

Wave 3 swarm_18b0d071 IS STACKED ON PR #1022, so check #7 was in CLAUDE.md when the implementer started. The implementer wrote a test with a name that claims:
1. TPPReauthenticatorPath — implies the test drives TPPReauthenticator's call site.
2. invokesPresentationViaSafelyPresent — implies the test reaches the production driver chain through TPPPresentationUtils.safelyPresent.

But the actual test body:
- Calls `presenter.presentSignInModalForCurrentAccount(...)` directly (line 237).
- Injects a fake driver that short-circuits before the production driver chain runs.
- Never instantiates `TPPReauthenticator`.

The test verifies "publish state + clear on completion" — which is fine. But the NAME promises the wiring, and the docstring even admits the bypass. A reviewer (or future maintainer) reading "TPPReauthenticatorPath_invokesPresentationViaSafelyPresent" reasonably believes the test pins those things; it does not.

This is the SAME shape as cs_847892e8 arch1 (the AudiobookSessionManager.swift:684-710 fake-wiring test). The system's permanent fix (CLAUDE.md DoD check #7) DID NOT prevent recurrence — the implementer either didn't read it or wrote the test before reading it and didn't go back to fix the name.

## Walls that should have caught it (and why they didn't)

- **contract**: The contract DID require the wiring-claim — "test #3 (`testPresenter_TPPReauthenticatorPath_invokesPresentationViaSafelyPresent`) is for exactly this." The contract specified the test by name but did NOT specify a grep that would catch a fake-wiring implementation. A grep-able verification criterion like `grep -B 3 -A 10 "testPresenter_TPPReauthenticatorPath_invokesPresentationViaSafelyPresent" <test-file> | grep -c "TPPReauthenticator("` ≥1 would have flagged this at Phase 4.5.

- **implementer DoD**: The implementer pasted DoD check #7 evidence as "Test #3 cites 4 production lines (A-D) in `present(state:libraryID:completion:)` and asserts each via `recorder.values` + `fakeDriver.capturedLibraryIDs`." That's the EXTRACTED helper, not the production driver chain. The implementer's evidence is honest about what it verifies, but the test NAME promises more. **The mismatch between name-promises-X and evidence-shows-Y is the failure.**

- **orchestrator skeptic pass (Phase 4.5)**: Phase 4.5 check 5b (added in PR #1022) says "for every claimed production-seam test, confirm the body calls the production entry point AND has no early-return mock that bypasses the cited line range." This IS the right check. The orchestrator either skipped this check or ran it without catching the SignInModalLifecycleTests case. Need to verify whether the check was even runnable (it's documented in the SKILL but may not have a concrete script).

- **QA reviewer**: QA flagged this as a WARNING (`rev_908b3450` finding 1), not a block, citing "mitigated by the migration is a single-line change at TPPReauthenticator.swift:54, grep-visible to any reviewer." That's a reasonable judgment call for QA — but the architect's higher bar is correct here. **CLAUDE.md DoD check #7 says "treat as a check #3 failure"** — that's a block, not a warning.

## Proposed permanent fix

**Fix 1 — Orchestrator Phase 4.5 check 5b becomes runnable, not just documented.**

Today it's a description; convert it to an actual grep that runs at integration time:

```bash
# Phase 4.5 check 5b implementation
for testfile in $(git diff --cached --name-only | grep -E "PalaceTests/.*Tests\.swift$"); do
  # For each multi-step-named test in the diff, extract the test body
  python3 ~/harness/core/lib/check-test-name-vs-body.py "$testfile" || {
    echo "BLOCK: $testfile has multi-step test name that doesn't match body"
    exit 1
  }
done
```

The `check-test-name-vs-body.py` script:
- Parses test method names containing multi-step verbs (`Path`, `via`, `through`, `invokes`, `roundtrip`, `across`).
- Extracts the production-class noun from the name (e.g. `TPPReauthenticatorPath` → `TPPReauthenticator`).
- Greps the test body for that noun being instantiated or called.
- Fails if the body doesn't reference the noun.

This would have caught wave 3 Module A's test name BEFORE review.

**Fix 2 — Add wall-failure-derived greps to the contract template.**

Add to swarm SKILL.md Phase 1 architect prompt:
> "For every test name in your contract's `## Test contracts` section that contains a noun-class-reference (PascalCase class name embedded in the test name like `TPPReauthenticatorPath`, `ViaAuthCoordinator`, `OnTPPNetworkExecutor`), add a verification-criteria line: `grep -c '<noun>(' <test-file>` ≥ 1. This is a literal check — orchestrator runs it; implementer pastes evidence."

**Fix 3 — Implementer DoD check #1 (SUT-instantiation) becomes more granular.**

Currently check #1 says "for every test file named `<SUT>Tests.swift`, grep for `<SUT>(`". Extend to:
> "Also for every individual test METHOD whose name embeds a class-noun (e.g. `testX_YPath_invokesZ` embeds `Y` and `Z`), the same test method's body must call `Y(...)` or `Z(...)` (or in the case of static methods, `Y.method(...)` or `Z.method(...)`). If the test name embeds a noun that the body doesn't touch, the test is fake-wiring per cs_847892e8 arch1 + cs_9a267b63 arch1."
