# Backtest — would SoD reviewers have caught the last 90 days of shipped Palace iOS bugs?

## Why this exists

PR #1018 (swarm_66819d80) was the first time both SoD reviewers actually
BLOCKED with substantive findings (catalogued in the six `2026-05-27-pr1018-*`
entries). That established the reviewer agents are not rubber-stampers in the
adversarial limit. The next question is whether their checklists actually
**generalize** — would they have caught the bugs that *did* ship over the
prior 90 days, or would they have approved most of them just like every
other process gate did?

This is paper analysis. We are not invoking the agents against historical
changesets — that would corrupt the audit trail (and require reconstructing
the changeset state at the time of the original PR, which we don't have).
Instead we reconstruct what the reviewer would have *seen* (diff shape,
existing tests, evidence) and assess against the prompt's checklist what
verdict the agent would have rendered.

The value of this report is **prompt-improvement recommendations**, not the
catch-rate number. The catch-rate has obvious noise: a single ambiguous case
moves it 10%. What matters is: of the WOULDN'T-CATCH bugs, which ones cluster
around a missing reviewer lens, and what addition to the prompt closes that
gap.

## Methodology

For each bug:

1. **Reconstruct what the reviewer would see** — file:line where the bug lived,
   diff shape of the PR that introduced or shipped past it, what tests existed
   in that PR, and what evidence the commit body documented.
2. **Walk the reviewer prompt's checklist.** Quote the specific item that
   would have flagged the bug (or the gap that would have let it through).
3. **Render a verdict.** WOULD CATCH / MIGHT CATCH / WOULDN'T CATCH /
   INSUFFICIENT DATA. The verdict is the union of *both* reviewers — if either
   would have blocked, the bug is caught.
4. **For WOULDN'T CATCH:** propose a concrete prompt addition.

Verdict glossary:

- **WOULD CATCH** — a specific checklist item maps to the bug. The reviewer
  would have written a `concern`/`fail` finding and blocked.
- **MIGHT CATCH** — the lens exists but applying it requires extra attention
  to a detail the prompt doesn't explicitly demand. Coin flip.
- **WOULDN'T CATCH** — the bug class is outside the reviewer's frame. No
  checklist item flags it; the reviewer would approve.
- **INSUFFICIENT DATA** — the original diff or test state isn't reconstructable
  with enough confidence to assess. Excluded from rate calculation.

Bugs from the current session (PR #1018) are excluded because we already
know the answer (BLOCKED). The point of this exercise is the historical lens.

## Bug 1 — PR #890 BorrowReducer missing `.downloadNeeded` case (F-011)

**PR / commit:** #890 (Phase 7 MBDC decomposition), commit `6ba8717b0`
**Shipped to:** release/3.1.0; fixed 2026-05-14 in manual regression
**File:line:** `Palace/MyBooks/BorrowReducer.swift` — switch on
`TPPBookState` had `.unregistered`, `.downloading`, `.downloadFailed`,
`.downloadSuccessful`, `.holding` cases plus `default: break`. Missing
`.downloadNeeded` arm. Source: `phase7_borrow_path_regressions_2026_05_14.md`.

### What an architect reviewer would see

- 41 commits / 1,524 LOC delta on critical-path borrow code
- Switch with a `default: break` — sized as a refactor where every branch was
  enumerated *except* the catch-all
- Tests: `BorrowReducerTests` covered each named case, mutation kill rate
  passed on the file

### Architect prompt walkthrough

The architect prompt has:
- "Does this fit the existing pattern" — yes (it does; that's why it wasn't caught)
- "Cross-module changes warrant scrutiny" — Phase 7 was a single-module
  extraction inside MyBooks
- "Critical-path code MUST have tests" — it had tests, the tests were just
  insufficient for missing-case detection

No checklist item maps to "switch with `default:` over a closed enum is
unsafe under refactoring."

### QA prompt walkthrough

QA's edge-case list includes "empty arrays, nil values, error responses,
expired tokens, malformed data, concurrent access, network failures."
*Missing enum case* isn't on the list, and per the memory: "Mutation testing
on the reducer file can't catch a *missing* case — mutation flips existing
operators, it doesn't add branches." The mutation discipline lens would
approve.

### Verdict: WOULDN'T CATCH

### Prompt addition

To architect prompt, under **Architecture**:
> When the diff contains a `switch` statement over a closed enum (`TPPBookState`,
> `LoadState`, etc.) with a `default:` branch, BLOCK and require the switch be
> exhaustive (no `default:`) OR require a parameterized test that iterates
> `.allCases` and asserts the expected behavior on every case. This is a
> structural guard against the F-011 class of decomposition bug.

This single item also catches `BookButtonMapper.SAMLStarted` falls-through
(documented as latent in the same memory).

## Bug 2 — PR #890 BorrowOperation inverted `attemptDownload` condition (F-014)

**PR / commit:** #890, same Phase 7 batch
**File:line:** `Palace/MyBooks/BorrowOperation.swift:401`
**Pre-extract:** `if attemptDownload && mapping.state == .downloadNeeded`
**Post-extract:** `if attemptDownload && mapping.state != .downloadNeeded`  ← inverted

### What an architect reviewer would see

- Same 41-commit Phase 7 PR
- A condition flipped during extraction
- A test (`testBorrowAsync_attemptDownloadTrue_callsDelegateStartDownload`)
  that *did* assert the correct invariant but ran late in the suite and was
  reclassified as a "timing flake"

### Architect prompt walkthrough

Architect prompt section **Verification**: "For non-tested changes: is the
verification approach documented in the commit body? 'I ran it locally'
without specifics is insufficient." The test existed, so the prompt's lens
would say "tested, good." It doesn't ask "did any test that *failed* on
this branch get reclassified as a flake?" — which is the actual signal that
would have caught this.

### QA prompt walkthrough

QA prompt under **Regression risk**: "For test-only changes: are the new
tests resilient to flakes? `Thread.sleep`, hardcoded timeouts, real
network/keychain access (vs. mocks) are flake amplifiers." This is the
*right neighborhood* — the test was using `await MainActor.run` under suite
saturation. But the prompt frames flakes as a hygiene issue, not as a
"flake on a critical-path test is a real-bug suspect" issue.

### Verdict: MIGHT CATCH

A diligent reviewer who actually *ran* the test suite (the prompt says
"don't run tests — that's CI's job") would have seen the flake and dug in.
But the prompt explicitly tells the reviewer not to run tests, so they'd
defer to CI's pass/fail, which had the flake-tolerant verdict.

### Prompt addition

To QA prompt, under **Regression risk**:
> If the diff touches a critical-path module (borrow, sign-in, download,
> DRM fulfillment, audiobook playback) AND a test in that module is
> currently classified as a "timing flake," BLOCK pending a root-cause
> diagnosis. The first hypothesis for a flake on a critical-path test must
> be "is the production code broken in a way that exposes only under
> timing pressure?" before "let me widen the timeout." Cite F-014
> (Phase 7 / PR #890) as the canonical case.

## Bug 3 — Marketplace LCP audiobook MIME-nesting (PP-4407)

**PR / commit:** #972 / `ca2ff13b6` (3.0.3 hotfix), shipped fix
**Bug-introducing PR:** original `LCPAudiobooks.canOpenBook` predicate (older;
the bug was latent until Marketplace landed deeper-nested MIME chains).
**File:line:** `LCPAudiobooks.canOpenBook` checked only
`defaultAcquisition.type`, missed LCP MIME two levels deep.
Source: `reference_marketplace_lcp_mime_nesting.md`.

### What an architect reviewer would see (on the original PR that wrote `canOpenBook`)

- A predicate that asks "is this book LCP?" by checking the top-level type
- No test covering nested `indirectAcquisitions`

### Architect prompt walkthrough

The architect prompt has **Risk** ("Blast radius if this breaks: local file?
Module? App-wide?") and **Architecture** ("Does it respect module boundaries?")
— neither flags "this predicate is too shallow for OPDS2's nested structure."

The architect *could* `forge_query_mind` for `anti-pattern` results in the
LCP/audiobook domain — the SharedMind verbatim is the canonical statement
that "acquisition-chain inspection must be **recursive by default** in this
codebase." But the prompt says "Optionally fetch SharedMind patterns" — it's
not mandatory. On a single-predicate change, an architect would likely skip
the SharedMind round-trip.

### QA prompt walkthrough

QA's **Edge cases** list: "Empty arrays, nil values, error responses,
expired tokens, malformed data, concurrent access, network failures."
*Nested data structures* aren't on the list. A QA reviewer would not
specifically ask "do the tests cover acquisition chains > 1 level deep?"

### Verdict: WOULDN'T CATCH (without the SharedMind query)

### Prompt addition

To architect prompt, in the **Optionally fetch SharedMind patterns** section,
upgrade to *mandatory* for specific modules:
> For diffs touching `LCPAudiobooks`, `LCPPDFs`, `MyBooksDownloadCenter`,
> `LCPClient`, `AudiobookLoader`, or any code under `Palace/OPDS2/`,
> MUST run `forge_query_mind context="acquisition chain recursive
> predicate" domain="Audiobooks|LCP"` and surface findings as a separate
> review section. These are the modules where MIME-nesting and
> acquisition-chain depth has historically caused silent bugs (PP-4407,
> PP-4454).

To QA prompt, under **Edge cases**:
> For predicates that inspect OPDS acquisition data, the edge-case list
> must include: (a) MIME-nested types ≥ 2 levels deep in
> `indirectAcquisitions`, (b) chain-types where the same MIME appears at
> multiple levels, (c) the predicate must be tested against a Marketplace-
> shape fixture, not just the legacy OPDS-1.x fixtures.

This prompt addition also would have caught PP-4454 (the structural mirror
fix for PDFs, shipped via PR #1008 four weeks after the audiobook fix
shipped — the bug existed in PDFs the entire time but nobody asked
"could the same shape apply to other content types?").

## Bug 5 — LCPStreamingPlayer continuation misuse crash (3.2.0)

**PR / commit:** crash introduced by PR #177 (commit `85ba6037`), latent
since PR #167 (`1926b614`)
**File:line:** `LCPStreamingPlayer.playCallback(at:completion:)` schedules a
30s timeout AND a seek callback; both can fire `completion`.
`OpenAccessPlayer.play(at:) async` wraps in
`withCheckedThrowingContinuation` → double-resume traps.
Source: `lcp_player_continuation_misuse_2026_05_26.md`.

### What an architect reviewer would see (on PR #177)

- "Migrate Player protocol to async/await (T1 of swarm_efd1f0c3)"
- A bridge that wraps `playCallback` in `withCheckedThrowingContinuation`
- Tests that cover the happy path

### Architect prompt walkthrough

Architect **Risk**: "Blast radius if this breaks: local file? Module?
App-wide? Public API?" — wrapping a callback in a continuation is a public-
API change at the player layer. The prompt would flag it as moderate risk.
But it doesn't say "every callback being wrapped in a continuation needs
an audit for multi-call paths."

Architect **Verification**: "How is the change verified? Tests?" — the
tests existed, they just didn't include the double-fire scenario because
the *existing source bug* (timeout + late seek both firing) was latent and
inert under the old callback shape.

### QA prompt walkthrough

QA **Edge cases**: "concurrent access" is listed. The double-fire scenario
is a concurrency edge case. A QA reviewer thinking about concurrency might
ask "what if the callback fires twice?" — but only if they specifically
think about the `withCheckedContinuation` contract (which traps on double-
resume). The prompt doesn't surface this contract.

### Verdict: MIGHT CATCH

A QA reviewer who reads Apple's `withCheckedContinuation` docs would flag
this. A QA reviewer who treats continuations as a black box wouldn't.

### Prompt addition

To QA prompt, under **Edge cases**, add a Swift-concurrency-specific section:
> For diffs that introduce `withCheckedContinuation` /
> `withCheckedThrowingContinuation` / `withUnsafeContinuation` /
> `withTaskCancellationHandler`, MUST audit:
> - Every callback path the continuation wraps for "could this fire
>   completion more than once under timing pressure?"
> - Test must include a scenario where the underlying callback fires
>   twice (one early via timeout, one late via real completion). If the
>   continuation traps under the test, the bridge needs a once-guard.
> - Cite `lcp_player_continuation_misuse_2026_05_26.md` for the canonical
>   pattern (NSLock-backed `makeOnceCompletion`).

## Bug 6 — CarPlay SIGABRT on iOS 26 (PR #968)

**PR / commit:** crash existed in pre-PR #968 code, fixed by PR #968 /
commits `5f9c19055` + `6766fb1e2`
**File:line:** Every CarPlay state-mutating call in `Palace/CarPlay/` used

`AudiobookSessionManager.openAudiobook` (errorPublisher + return .failure).
Source: `carplay_crash_3_1_0_build_476.md`.

### What an architect reviewer would see (on the original CarPlay PRs)

- New CarPlay code with `completion: nil` everywhere — looked idiomatic
  pre-iOS 26 (the iOS 25 docs didn't mandate completion handling)
- Dual-channel error surface in `AudiobookSessionManager` — intentional per
  the memory ("openAudiobook failures need the result return; mid-playback
  errors need the publisher")

### Architect prompt walkthrough

The prompt doesn't have an OS-version-evolution lens. "Will this break on
the next iOS version?" isn't a checklist item. Pre-iOS 26 the
`completion: nil` pattern was acceptable.

### QA prompt walkthrough

QA's **Edge cases** list doesn't include "OS version transitions tighten
runtime contracts." A QA reviewer in iOS 25 wouldn't ask this.

### Verdict: WOULDN'T CATCH (the crash was a forward-time iOS contract change)

### Prompt addition (architect)

Add a new section to architect prompt:
> ### Platform contracts
>
> When the diff touches OS-framework APIs that have known evolution risk
> (CarPlay's CPInterfaceController, Network.framework, Combine,
> WidgetKit, FileProvider, BackgroundTasks), audit for:
> - Idiomatic uses of nullable completion handlers — iOS 26+ has tightened
>   several of these to raise on completion=nil + failure
> - Deprecation warnings in the diff or in symbols the diff calls
> - The minimum iOS deployment target the diff implicitly assumes vs. the
>   project's declared deployment target
>
> Cite `carplay_crash_3_1_0_build_476.md` (build 476 SIGABRT on iOS 26)
> as the canonical case.

This lens also would catch the dual-channel-error-surface aspect of the
bug if the reviewer reads the error-handling section the way the
SharedMind suggests.

## Bug 8 — `setAuthToken` doesn't clear `credentialsStale` (Icarus OIDC)

**PR / commit:** fix in `TPPUserAccount.swift:384-393`, shipped 2026-05-14
(no single bug-introducing PR — the asymmetry was the original design)
**File:line:** `TPPUserAccount.setAuthToken(...)` wrote new token to keychain
but did NOT flip `_authState` from `.credentialsStale` to `.loggedIn`. The
state survived across launches; next launch saw stale token + stale flag,
prompted re-auth even though bearer was valid.
Source: `investigation_icarus_oidc_auth_loss_2026_05_14.md`.

### What an architect reviewer would see (on the original `setAuthToken` PR)

- A setter that writes a token to keychain
- A separate setter (`setAuthState`) that writes the auth state
- The two are not coupled

### Architect prompt walkthrough

Architect **Architecture**: "Does this fit the existing pattern?" — yes, the
two-setter shape *is* the existing pattern. No flag for "these two pieces
of state should be coupled atomically."

Architect **Risk**: "Rollback path: can this be reverted cleanly?" —
nothing about persisted-state-across-launches.

### QA prompt walkthrough

QA **Edge cases**: "expired tokens" is on the list! A QA reviewer thinking
about expired-token recovery *could* ask "what state is the user in after
re-auth completes?" — but the answer requires knowing that
`_authState` is keychain-persisted and survives across launches. The
prompt doesn't ask "is any persisted state related to the change?"

### Verdict: MIGHT CATCH

### Prompt addition

To QA prompt, under **Edge cases**:
> For diffs that touch authentication, persistence (keychain, UserDefaults,
> Core Data, file system), or any state that survives across app launches,
> MUST audit:
> - What state is read on cold launch?
> - What sequence of events could leave that state inconsistent
>   (interrupted token refresh, app killed mid-write, sign-out without
>   token clear)?
> - Is there a "re-auth doesn't clear stale flag" or "sign-out doesn't
>   clear cached credentials" failure mode?
> - Tests must include a cold-launch step (simulated via fresh instance
>   construction with seeded keychain state), not just in-session state
>   changes.

This same lens catches the cross-library `currentUserAccount` vs
`userAccount(for:)` asymmetry at `TPPNetworkResponder.swift:308 vs :461`
(noted as a separate cleanup in the same memory).

Of 10 bugs assessed (PR #1018's bugs excluded as known-blocked):

| Verdict | Count | Bugs |

**Raw catch-rate: 0% definitive WOULD-CATCH, 30% MIGHT CATCH.**

That's a brutal number, and it's the right brutal number. The reviewer
agents as currently prompted are calibrated against the *generic-software-
engineering* lens (architecture / scope / verification / risk / discipline),
not against the *Palace-iOS-specific* lens (acquisition-chain recursion,
toolkit submodule risk, CarPlay completion contracts, persisted auth
state, SwiftUI alert binding deadlock, design review of copy).

The PR #1018 wins came from **process discipline** issues (fake test
instantiation, dishonest migration, half-done test) where the generic
lens is sufficient. Most Palace shipped bugs are **domain-knowledge**
issues where the generic lens isn't.

This is exactly the result we'd expect, and it tells us what to do.

### 1. Module-specific mandatory SharedMind queries (catches: #3, #4, #7) — 3 cases

Architect prompt currently says "*Optionally* fetch SharedMind patterns."
For specific modules (LCP, audiobook toolkit, CarPlay, OPDS2, sign-in
auth), make it **mandatory** with the specific `forge_query_mind` calls
spelled out. The prompt should include a per-module mapping:

| Module touched | Mandatory queries |
|---|---|
| `Palace/Audiobooks/*` or toolkit submodule bump | `audiobook toolkit playback regression`, `Audiobooks` domain |
| `LCPAudiobooks*`, `LCPPDFs*`, `LCPClient*` | `acquisition chain recursive predicate`, `LCP` domain |
| `Palace/CarPlay/*` | `CarPlay state mutation completion`, `CarPlay` domain |
| `Palace/OPDS2/*` | `OPDS2 nested indirectAcquisitions`, `OPDS2` domain |
| `TPPNetworkResponder*`, `TPPUserAccount*` | `auth state persistence keychain`, `Auth` domain |

**Why it works:** SharedMind already contains the verbatim distilled lessons.
The prompt just needs to make the query mandatory rather than optional for
the modules where the lesson density is highest.

### 2. Structural-sibling sweep clause (catches: #4, and reduces future P0 risk) — 1 case + recurrence guard

When a fix lands in `LCPAudiobooks`, the reviewer must demand the author
document whether the structural siblings (`LCPPDFs`,
`OpenAccessAudiobooks`, etc.) were audited for the same bug shape. PP-4454
is the textbook case: PP-4407 fixed audiobooks 4 weeks before PDFs got
caught. The lesson existed; the discipline didn't.

**Why it works:** the cost of "did you check the siblings?" is 30 seconds
of typing in the commit body. The cost of NOT asking is a second shipped
bug and a second hotfix.

### 3. Switch-over-closed-enum exhaustiveness clause (catches: #1, plus BookButtonMapper latent) — 1 case + 1 latent

When the architect sees `switch <enumExpr> { ... default: ... }` over a
known closed enum (`TPPBookState`, `LoadState`, `AccountState`, etc.),
BLOCK and require either exhaustive arms (no `default:`) or a parameterized
`.allCases` test. This is structural protection against the F-011
decomposition bug class.

**Why it works:** mutation testing literally can't catch a missing case,
which is documented in the F-011 memory. This requires a structural prompt
clause, not a coverage-quality one.

### 4. Swift-concurrency contract audit clause (catches: #5) — converts MIGHT to WOULD

When the diff introduces `withCheckedContinuation` or
`withCheckedThrowingContinuation`, MUST audit the wrapped callback for
"could this fire completion more than once?" and MUST add a test where
the underlying callback fires twice. NSLock-backed `makeOnceCompletion`
is the canonical pattern.

**Why it works:** the LCP continuation crash was latent for a month;
once a reviewer knows to ask the question, the answer is obvious.

### 5. Persisted-state cold-launch clause (catches: #8) — converts MIGHT to WOULD

When the diff touches authentication, persistence, or any state that
survives across app launches, MUST audit:
- What state is read on cold launch?
- What sequence of events could leave that state inconsistent?
- Tests must include cold-launch scenarios with seeded keychain state.

**Why it works:** the Icarus OIDC bug class is "in-session it'd work, but
the user's NEXT launch breaks." Without a cold-launch lens, the unit-test
mindset misses it.

## Honest limitations and caveats

1. **Reconstruction error.** For bugs I didn't fix myself, I'm inferring
   the original diff shape from the post-fix memory. The reviewer would
   have seen the *original* diff, not the after-the-fact summary. If the
   original diff had clearer signals (a comment saying "TODO: handle
   `.downloadNeeded` later"), the reviewer might have caught more.
2. **Reviewer-author judgment overlap.** In several of these cases, the
   PR author is also Maurice. If the author cuts a corner, the reviewer
   sees it; if the author's mental model is wrong, the reviewer often
   shares the same blind spot. Cross-author reviewer agents (different
   model, different prompt seed) might catch more.
3. **MIGHT CATCH is uncertain.** The three MIGHT-CATCH bugs depend on
   reviewer attention to subtleties the prompt doesn't explicitly demand.
   In practice, a reviewer being run in a swarm under time pressure
   would probably approve all three. The prompt-addition recommendations
   convert them to WOULD CATCH definitively.
4. **No live test of post-update prompts.** This report identifies the
   gaps; we haven't yet rerun the analysis with the updated prompts to
   verify they actually flip the verdicts. That's the next loop: add the
   prompt additions, re-walk the bugs, see if the catch-rate moves.
5. **Sample selection bias.** The bugs in this report are the ones that
   got documented in MEMORY.md. Bugs that didn't generate a memory entry
   (because they were "obvious" or "easy") aren't here. The agent
   probably DOES catch obvious bugs (the PR #1018 wins are evidence). So
   the true catch-rate is probably higher than 0%; it's just that the
   visible-bug subset is hard-mode.
6. **Catch-rate isn't the goal.** A reviewer that catches 95% of bugs
   by blocking 50% of clean PRs is worse than one that catches 30% and
   only blocks the actual problem PRs. The prompt additions above are
   targeted at *high-density* bug classes (LCP, audiobook toolkit, auth
   state, CarPlay) so they shouldn't dramatically raise false-positive
   blocks on clean PRs in other areas.
